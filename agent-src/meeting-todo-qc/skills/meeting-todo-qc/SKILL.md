# 会议待办质检（meeting-todo-qc）

## 这个技能解决什么

AI 从会议转录里提取的待办，常见三类问题：依据是概括而不是原话；该派出去的活漏了；负责人和截止时间留空却其实原文有线索。这三类直接决定待办能不能建进任务系统，而**生成环节自己查不出来**——同一个模型、同一种读法重读一遍，看到的和第一次一样。

所以这个技能不"再生成一遍"，而是**换一种表示去校验**：

- 把原文依据当字符串逐字回查，找到就是找到，找不到就是找不到，不靠模型判断；
- 把转录按人切片、逐句找"谁被派了活"，产出**候选**而不是结论；
- 逐条看四个要件（动作 / 责任人 / 截止 / 依据）缺哪个，缺的能不能从原文线索补。

## 第一步：等待用户上传会议转录

**不要假设工作区里已经有转录文件，也不要凭猜测构造示例数据。** 先请用户上传或粘贴会议转录，并在这一步把三件事说清：

1. **说话人标记**：转录需带 `张三：……` 这类说话人前缀，按人切片的遗漏检查才成立。没有标记时，依据校验与字段核查仍可用，但要明确告诉用户"遗漏检查这一层不可用"，不要悄悄降级。
2. **是否已有待办表**：已有就一起给（6 列：编号 / 任务 / 负责人 / 截止时间 / 约束 / 原文依据）；没有就由本技能先提取一版，再对自提版做质检，并在输出里标明"待办由本技能提取，质检对象与生成方同源"这一局限。
3. **脱敏提醒**：真实会议内容涉密时先脱敏再粘贴。

拿到转录之前不要开始质检。

### 材料是录音时怎么进来

本技能不做语音识别，只处理识别结果。录音在本机由 DuMate 的会议能力转写（录音结束后取转写原文），拿到文字后再进来质检；技能里不另接识别模型，也不上传音频。

若用户给的是转写平台导出的稿子，常见形态是：行首带 `[00:01:23]` 或 `00:01:23`、一轮发言一行、句子没有句末标点、夹着 `[听不清]`/`[笑声]`/`[noise]` 这类占位。**直接收下，不要要求用户先手工整理**——本技能能认出这种形态，并按下文口径自动去噪后再比对。

## 第二步：确认输入形态

| 情况 | 做法 |
|---|---|
| 有转录 + 有待办表 | 直接质检（第三步起） |
| 有转录 + 无待办表 | 先按下面的提取规则生成一版，再质检；输出里标注同源局限 |
| 只有待办表、无转录 | 只能做字段完整性（C）与结构检查；D/A 两层无法执行，如实说明 |
| 转录无说话人标记 | 执行 D 与 C；A 跳过并说明原因 |
| 录音识别稿（ASR 导出） | 先出转写质量体检（第五步前的体检段），再按去噪口径跑 D/C；有说话人标记才跑 A |
| ASR 稿且没有「参会人：」行 | 从说话人标签反推名单，只认出现 ≥2 次的 1–4 字真名（不认「说话人1」）；反推不等于完整名单，必须提示核对 |

提取待办时保持四条硬规则：只依据原文、缺失填"待确认"、原文依据逐字引用、讨论性表述不提取。

## 第三步：D 通道 · 逐字回查原文依据

用脚本跑，不要肉眼比对——字符串匹配是确定性校验，交给机器更可靠。

```bash
python scripts/qc_tools.py <转录.txt> --table <待办表.csv>
```

输出会给出每条依据是否命中、以及不命中时的原文对照。判读规则：

- **不命中即硬结论**：这是概括、改写或者引用了转录里没有的句子。不要替它辩护成"意思一样"。
- 常见成因是漏字、把两句话拼成一句、或引用了不在本次转录范围内的段落（跨会议引用）。
- 忽略空格差异是合理的（语音转写里空格不可靠），但不能放宽到同义词级别。
- 录音识别稿还要另做一层格式去噪：行首时间码、说话人前缀、`[听不清]` 这类占位、句末标点都算格式，去掉后再比对；**只去格式，不改用词**。同音错字属于识别误差，不要用归一化替它掩盖——它会继续表现为不匹配，这是正确结果。
- 同一份稿子可以跑两遍对照：去噪后命中、严格比对（关闭归一化）时不命中，说明差距来自格式噪声，不是依据被改写。这个对照比单次结果更能说服人。

## 第四步：A 通道 · 按人切片查遗漏候选

```bash
python scripts/qc_tools.py <转录.txt> --demo        # 用内置示例跑通，确认环境可用
python scripts/qc_tools.py <转录.txt> --table <待办表.csv>
```

脚本依赖转录里的 `参会人：` 行确定"谁被点名"，缺这一行时 A 通道不启动。

**这一层只出候选，不下"遗漏"结论。** 报给用户时必须保持这个措辞，并逐条给出：

- 被点名的人、置信度（高/中）、触发它的原句；
- 为什么可能已被现有条目覆盖（"牵头"方视为管理角色、应答句并入上一句、收件人不算责任人）；
- 采纳与否由用户裁决。

误报的典型形态（在公开语料上几乎全是这几类）：邀请句（"请 X 介绍一下"）、名单句、回溯引用（"刚才 X 说的"）。这三类已由脚本规则①②整句排除；带指派的句子（"参加的有张三、李四，张三你把方案写一下"）有豁免，不会被误排。v1.4 另加规则④受邀对象剥离（"把 X 和 Y 都叫上"）、⑤主持人复述句、⑥回溯疑问句（"你之前是不是整理过？"）。

**另一种相反的错误：候选归零但确有遗漏。** 一句里两个动作被表内一条条目吸收时，旧覆盖判断会判"已覆盖"。v1.4 用动作否决修正：任务列含成果类动词（制作／公布／起草／交付…）而候选句一个动作词都不共享，就不算覆盖。第 4 组因此从 0 条回到 1 条。代价是同句两人时人物归属按句级判（会标错成句子里先出现的人），**必须交人工改判，不能直接采信**。

责任落在机构（"财政部／我们／相关部门"）时，脚本单列一段**机构主体清单**，用"机构（个人待确认）"占位。这一段只作提醒，**不进候选表、不计精确率**，不能拿来充召回；其他角色词（"客服那边"）仍捞不到，要提前说明。

## 第五步：C 通道 · 字段完整性

统计"待确认"在负责人与截止时间两个字段上的分布，然后分成两类：

- **原文确实没有**：合理留空，保持"待确认"，不要编造。
- **原文有线索但没被用上**：这是真问题。给出线索原句，并说明可补成什么。

判断截止时间时格外小心：会议里常出现"周五上午我去锁场地"这类**动作时点**，它不是这件事的截止时间。拿不准就退回"待确认"，不要为了填满字段而升级。

## 第六步：给修正建议

按"补 / 改 / 注"三类给，逐条挂到原编号上：

- **补**：补入遗漏的明确行动项；补负责人或截止时间时附线索原句。
- **改**：把概括的依据换成逐字原句；把动作时点从截止时间里撤回。
- **注**：讨论性表述要保留时，在约束列注明"原文为讨论性表述，是否执行需人工判断"，而不是直接删掉。

每条修正都要能回答"依据是哪句"。给不出的，就别改。

## 第七步（可选）：组织视角

待办最终要落到人身上，按人聚合比按条看更能暴露问题：

```bash
python scripts/org_view.py <待办表.csv> <转录.txt>
```

输出三块：按人负载（含风险分）、风险排序、补字段队列。风险分的权重口径见 `references/判定手册.md`。

把它当作"这些活压在谁身上、哪几条必须先补字段"的判断依据，而不是绩效考核。

## 第八步（可选）：双人标注一致率

用户要做质量度量、或需要向别人证明判定口径可复现时：

```bash
python scripts/agreement.py <标注员A.csv> <标注员B.csv> --out 一致率.txt
```

标注模板是 6 列加标注人。**口径必须说准**：这是条目级一致率 + 字段一致率，**不是 Kappa**——条目级标注算不出 Kappa 需要的期望一致率。建议先自己填两份再让别人填，用来检验判定手册是否写清了。

## 输出模板

```markdown
## 质检结论
- 输入：转录 X 字符 / Y 句 / Z 位发言人；待办 N 条（来源：用户提供 / 本技能提取）
- D 依据可追溯：a/N 命中，不命中条目与原因
- A 遗漏候选：k 条（每条含人物、置信度、原句），已排除的误报形态
- 机构主体清单：m 条（责任在机构而非个人，单列，不计精确率）
- C 字段完整性：负责人待确认 p 条、截止时间待确认 q 条，其中可补 r 条
- 结论：可直接建单 / 需补字段 / 待人工判断各多少条

## 逐条明细
（表格：编号 / 问题类型 / 具体描述 / 依据原句或判断理由）

## 修正建议
（补 / 改 / 注 三类，逐条挂原编号）

## 边界
- 哪些层没执行、为什么（缺说话人、缺转录等）
- 语料性质与适用范围
```

## 口径与边界

- **"可直接执行"与"可直接建单"不是一回事**：前者指四个要件齐全，后者指能直接建进任务系统。汇报时分开说，否则会被当成前后矛盾。
- **真实内部会议的召回率无法由本技能自证**：如果语料是构造的或公开的，必须标明。公开的中文会议语料（发布会、论坛、沙龙）几乎不含"人名 + 指派"结构，A 通道在上面会大面积误报，这不代表技能失效，而是语料不适用。
- **适用**：有人被点名、有事被分派的内部分工会议。
- **不适用**：对外发布会、学术分享、访谈——里面没有"谁在什么时候做什么"。
- 录音转写不在本技能范围内；需要转写时先解决转写，再回到第一步。

## 一键入口（v1.2 新增）

`scripts/qc.py` 把四层串成一条命令，不必分开跑 `qc_tools.py` 与 `org_view.py`：

```bash
python scripts/qc.py --check                                  # 环境自检：模块能否导入、样例在不在
python scripts/qc.py --demo                                   # 内置样例跑通，先确认能看到报告
python scripts/qc.py --transcript 转录.txt --todo 待办.csv --out 质检输出
```

产物三件：`报告.md`（四段式，可直接给用户看）、`质检标注.csv`（逐条复核标记，不改原值）、`摘要.json`（计数）。
`qc.py` 只做编排，判定逻辑仍在 `qc_tools.py`（D/A）与 `org_view.py`（风险分档），改规则仍改这两处并同步对拍。
